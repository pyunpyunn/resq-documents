Start here: how to use this guide

Think of RESQPERATION as two user-facing applications that send requests to one backend, which checks the request, applies rules, and reads or writes operational data.

How to present it: explain one flow at a time: (1) who starts it, (2) which screen and API are involved, (3) what the backend verifies, (4) where information is stored, (5) what response or notification comes back. You do not need to claim that every optional service is running in every deployment.

Evidence labels used below

  • In source The repository contains implementation code or configuration for the behavior.
  • Needs configuration The code exists, but an endpoint, credential, service, worker, data asset, or permission must be configured.
  • Not established Source files or design documents do not prove a live partner connection, delivery, production deployment, or field acceptance.
Important: a package, URL, sample environment setting, architecture diagram, or successful provider response is not by itself proof that a feature is operational in the deployed system. The implementation and the environment must both be checked.

1. System architecture: what, how, where and why

What: a browser-based operations dashboard and an Expo mobile application (used by household and responder accounts) share a Laravel API. The API is the security and business-rule boundary. Clients should not connect directly to the production database.

How: clients send JSON over HTTP(S); the backend authenticates and authorizes the caller, validates input, runs a workflow, persists data, and returns a structured response. Long-running notifications and partner handoffs can use queues.

Where: the web application is under resqperation-system/frontend-web, the mobile client under resqperation-system/frontend-mobile, and the API under resqperation-system/backend-laravel.

Why: a single backend lets web and mobile share identity, permissions and operational records, and makes server-side checks authoritative instead of trusting a client screen.

Typical read flow

  1. A user opens a screen.
  2. The client API helper makes a request with the current authentication token.
  3. Laravel checks the route middleware and caller permissions.
  4. A controller delegates to a workflow/query/service.
  5. Backend code reads permitted records and shapes a response.
  6. The client renders the response or an explicit error/loading state.

Typical write flow

  1. The user submits a status, report, dispatch or request.
  2. The API validates payload and access rights.
  3. A workflow applies business rules and records the change.
  4. Audit/outbox/job work may record the action or notify recipients.
  5. The API returns the saved state; the client refreshes its view.

2A. Where code lives: file tree, backend flow and how files connect

A feature is usually split across files because each file has one job. For example, a controller should translate HTTP into an application call; it should not also contain the whole user interface, permission catalog, every SQL query and response formatting. Laravel's dependency container connects the classes when a request arrives.

Visual runtime map: config, database, routes, storage, vendor and env

These are different responsibilities: environment values supply deployment-specific settings; configuration files organize those settings; bootstrap loads the application and route registries; Composer installs PHP dependencies; database migrations define structure; storage holds runtime files.

How to explain the “backend words” without mixing them up

  • Environment: .env holds machine-specific values such as selected DB connection, host, user, password, API keys, debug mode, queue/cache/session driver and service URLs. .env.example is a starter template, not the live environment and not proof a service is connected. Copy it to a private .env, set safe values, and never commit real secrets. Keep APP_DEBUG=false in production. Do not expose server credentials in a mobile/web build.
  • Configuration: files under config/ group environment values and defaults. Example: config/database.php reads DB_CONNECTION to choose a named connection and reads the matching connection settings. Feature/runtime code should normally query Laravel's config(...), not read environment variables throughout the app. A cached configuration snapshot can be built for deployment; clear/rebuild it after changing deployment settings so the running app sees the intended values.
  • This project's DB selection: the example sets DB_CONNECTION=resq_local. config/database.php maps that alias to the local operational DB values. It also declares other connections (including shared ResQ and TrackingAid); a connection definition alone does not mean the database is reachable or actively used. The shown household API uses the default connection via Laravel DB/query-builder calls. Actual deployment values and grants must be checked privately.
  • Database vocabulary: a database server (for example MySQL) hosts one or more databases; a database contains tables; a table has columns and rows. A primary key uniquely identifies a row; a foreign key links related rows; an index speeds selected lookups; a migration changes the schema (structure); a seeder inserts initial/reference data; a transaction groups writes so commit saves all or rollback undoes all. database/migrations contains schema instructions—not the live operational records.
  • Routes: routes/api.php describes HTTP method + URL + controller + middleware. Laravel loads it through bootstrap/app.php; its v1 prefix is part of the client URL. A route is not a database table or service class.
  • Storage: storage/ is runtime space for logs, framework cache, sessions/files and generated artifacts depending on the configured driver. Treat private uploads and generated reports as protected data, ensure write permissions/retention/backups, and do not confuse the storage/ directory with a database.
  • Vendor: composer.json declares allowed dependency ranges, composer.lock records exact resolved versions, and composer install installs them under vendor/ plus the Composer autoloader. Do not hand-edit vendor/; change the manifest through Composer and deploy the lock-consistent install.
  • Runtime companions: queue jobs execute only when the selected queue driver/worker is configured; scheduled commands execute only when the scheduler runs; cache and sessions use their configured drivers. The example environment defaults several paths to local/synchronous development behavior, while deployment may intentionally differ.

Source links: application bootstrap, API routes, scheduler definitions, database connection definitions, queue configuration, filesystem configuration, safe environment template, Composer dependency manifest, application service provider.

How to trace another module during a coding test

  1. Find the screen in frontend-web/src/pages or mobile app//components/.
  2. Find its API call in that platform's api/ folder.
  3. Search the exact URL/method in Laravel routes/api.php; record middleware and role.
  4. Open the controller action; follow the service/workflow call rather than assuming business logic is in the controller.
  5. Follow its Query/Action/Model/Writer and migrations to identify tables and writes.
  6. Follow the presenter/resource to the JSON response and the UI's success/error handling.
  7. Find focused tests under backend tests/ and client tests/.

End-to-end integration checklist

  1. Identify the record and system of record (who owns the authoritative value).
  2. Show the route/client/payload mapping and which fields are transmitted.
  3. Confirm the auth mechanism and configure secrets only on the backend, never in the mobile bundle.
  4. Confirm network access, database permissions or API reachability in the actual deployment.
  5. Run a test exchange and capture correlation/tracking ID, timestamp, response and error behavior.
  6. Get partner-side confirmation that the record was received and acted on.
  7. Test retry/idempotency and explain how duplicate submissions are prevented.

Network route: client to Laravel to the database

Web browser or native phone
├─ DNS / IP / port / Wi-Fi, LAN, Tailscale or public HTTPS route
├─ HTTPS in deployed public use (private/local development can use HTTP)
├─ Web CORS origin check / API host and request-header guard
├─ API edge limit and Laravel API middleware
├─ route-level authentication / role / device / module policy
├─ controller → workflow → database/provider client
└─ JSON status + headers → client updates UI or displays explicit failure

Never: browser/mobile app → direct MySQL connection. DB usernames/passwords stay on the backend.

Web: the shared Axios client chooses the API URL from VITE_API_BASE_URL and browser host. Local Vite development proxies /api and /storage to Laravel at 127.0.0.1:8000; a non-local browser can use same-origin /api/v1. Vite is a development server/proxy, not the application backend.

Mobile: the client can use a configured API URL plus fallback URLs. It probes /api/v1/health/ready (4-second probe timeout, readiness cached for about 60 seconds) and selects a ready server. Android release candidates are prioritized as Ngrok HTTPS, private Wi-Fi IPv4, then Tailscale. Network failure can trigger another route for safe reads and login; ordinary writes are deliberately not blindly replayed against a second server because that could duplicate an operation. The API client checks the selected origin, adds a device UUID for bound rescuer requests, and uses a 20-second request timeout.

CORS: Cross-Origin Resource Sharing lets the backend allow known browser origins and request headers. The project's CORS config sets supports_credentials false, while the web Axios client does not use a cookie-based login flow. CORS is not authentication; the server must still authenticate and authorize the request.

Connections and failures: DNS resolves a hostname to an address; a port identifies a service; a tunnel/LAN/Tailscale route provides reachability; Laravel's readiness check distinguishes an API process from a healthy API-plus-database connection. HTTP 401 means authentication is absent/invalid, 403 means authenticated but disallowed, 404 means not found, 409 means state conflict, 422 means invalid input, 429 means throttled, and 5xx means server/dependency failure. The project can attach an X-Request-ID to help connect an API error to server logs.

What “session”, “token” and “cookie” mean here

  • API authentication used by clients: login calls Laravel; backend verifies the account/password and issues a Sanctum personal access token. Client stores that token and the Axios interceptor sends an Authorization: Bearer … header. Each protected request is authenticated against that token. Logout calls the backend to delete/revoke the current token, then clears the local copy.
  • Web token storage: token is stored in browser localStorage, which is browser key/value storage, not a cookie. JavaScript can read it, so frontend injection/XSS is a security concern; never store the backend secret key there.
  • Mobile token storage: native builds use Expo SecureStore (OS-backed secure storage); the mobile web build uses its web fallback, localStorage. Native and browser guarantees are different.
  • Laravel session cookie: Laravel still has generic session configuration (example environment says SESSION_DRIVER=file and a 120-minute lifetime), but the main React/mobile API requests use bearer tokens, not Laravel's session cookie. Do not describe the API login as cookie-session authentication without verifying a different client path.
  • Sanctum stateful SPA: Sanctum can also support cookie/CSRF authentication for first-party SPAs. That is a different mode, requiring CSRF-cookie request, session cookie, credentialed CORS and CSRF handling. The current web API client uses the token path and the CORS config disables credentials.
  • Redux “session”: this is the current in-memory account/cache scope, not the server's Laravel session. The client clears cached data on token/account/server change and on 401 logout/session expiration.
  • Remembered login: web stores the remembered account ID; if supported and permitted by browser security, the browser credential vault can handle the password. Native may store remembered credentials using SecureStore. Never place passwords into Redux or ordinary browser storage.

Evidence: web HTTP client, web token storage, web login/logout, mobile networking/failover, native secure storage, backend login/token issue/revoke, CORS settings, Laravel session settings, Sanctum settings.

Offline behavior: cached reading is not the same as offline writes

Online preparation (rescuer)
API bootstrap / assignments / household data / route geometries
→ save snapshot and active-pack manifest in native SQLite
→ download bounded map tiles on Wi-Fi (with progress/size checks)

When disconnected
local SQLite snapshot + downloaded map pack + GPS
→ render saved directions; record trip points locally
→ queue trip.start / trip.points / trip.end / selected household.status event

When connection returns
network check → ordered batches → POST /api/v1/mobile/sync
→ server verifies bound device/team/assignment + event UUID
→ server transaction applies event and records acknowledgement
→ phone deletes processed outbox events; failures remain visible locally
  • Map: the rescuer explicitly downloads the active map pack over Wi-Fi. MapLibre offline packs (or a supported imported local map pack) are versioned; previous version packs may be removed after the new pack completes; download size is bounded. An offline map is map data only—it does not itself fetch new road directions.
  • Routes: routes and dispatch snapshots must have been cached or downloaded while connected. Live rerouting/refresh needs the API and routing service. Existing saved route can still be displayed offline.
  • Trips: native SQLite stores trip metadata and GPS points. The local outbox has unique client event UUIDs; server processes event IDs idempotently in sync_events. Trip start must be acknowledged first because later point/end events need the server trip ID. GPS points are filtered for impossible coordinates, accuracy, timestamp, speed and minimum movement distance.
  • Queued field household status: the rescuer offline-navigation screen explicitly queues this event for /mobile/sync. It is a defined, authorized responder sync workflow. Do not infer that every household-app status submission or every other POST is queued offline; the ordinary household status API helper posts directly and must be online.
  • Retry: an unavailable network leaves pending local work. Sync batches are bounded, ordered and use backoff; the server returns acknowledgements. A rejected event is retained as a failed local record for investigation and may block dependent trip events rather than being silently reported as delivered.
  • Data reconciliation: local events are not authoritative server records until accepted and acknowledged. Show “saved on this phone / awaiting sync” distinctly from “saved to HQ”. Duplicate event IDs must not create duplicate server actions.

Database indexing: making common lookups faster

An index is an additional database structure that helps MySQL/SQLite locate rows without scanning an entire table. It speeds up matching/sorting columns used in real queries, but takes storage and makes writes slightly more expensive. A composite index covers multiple columns in a defined order; a query often benefits when it filters by the leftmost columns first. An index does not replace validation, authorization or a correct SQL query.

Example in migrationsTypical query pattern it can helpWhy column order matters
household_status_logs(disaster_id, household_id, submitted_at, status_log_id)Find a particular household's recent status history during an event.Event and household filters come first, then time/order.
responder_assignments(disaster_id, status, assigned_at, assignment_id)Find active dispatches for an event in assignment order.Common equality filters precede ordering columns.
notifications(user_id, is_read, created_at, notif_id)Load a user's unread/latest notification feed.User/read-state filters plus created-time ordering form the lookup prefix.
SQLite outbox(status, created_at) and local_trip_points(local_trip_id, recorded_at)Select pending local events or chronological points for one trip.Index begins with the column used to narrow the result set.

Laravel schema migrations add/check indexes only when tables/columns exist; migrations are the reproducible source of schema changes. To diagnose slowness, identify the actual SQL/query, check filter and sort columns, inspect existing indexes, use a query plan such as MySQL EXPLAIN, measure representative data and test before adding an index. Do not add a speculative index to every column.

“Indexing” can mean two unrelated things: relational DB indexes accelerate SQL queries; a search index/catalog is a separate full-text or document-search structure. This system's database index migrations are not proof that all text fields have a full-text search index. Global search is implemented by application queries/services and should be traced separately.

Evidence: operational MySQL indexes, mobile overview indexes, realtime read indexes, SQLite indexes.

11. Configuration, privacy, reliability and known limits

  • Environment-specific services: API host, database connection, partner integration credentials, SMS gateway, OneSignal, weather tokens, map/routing endpoints and worker settings are configured separately from source code.
  • Queues and schedules: queued broadcasts and partner handoffs do not finish unless the configured queue workers/scheduler are running. Monitor failures and retry state.
  • External service failures: tell users when a provider is unconfigured or unavailable; do not show a success state merely because a local request was stored.
  • Location and household information: is sensitive. Limit access to legitimate operational duties, explain device permissions and retention, and avoid personal data in screenshots, public repositories or logs.
  • Offline conditions: offline map assets do not make all API workflows offline. Cached views, unsent data, route packs and actual connectivity behavior must be tested separately.
  • Role/data freshness: screen permissions and external data depend on current account/role configuration and source timestamps.

Before telling the panel a feature is live, verify

  1. Which exact deployed app/backend version is running?
  2. Which environment and feature settings are active?
  3. Is the required queue, scheduler, map service or provider running?
  4. Can a test device/account perform the action under its real role?
  5. Does the expected record appear in the system of record?
  6. Can you show timestamps, logs, acknowledgement or test evidence?

GeoJSON / geometryGeoJSON is a JSON format for points, lines and polygons; geometry is the spatial shape itself.
Boundary / bounds / bounding boxBoundary is an area polygon; bounds are coordinate limits, often a rectangle. Bounds do not prove an official polygon.
Geocoding / reverse geocodingGeocoding turns a place/address into coordinates; reverse geocoding estimates a place/address from coordinates.
Routing / route geometry / ETARouting finds a path on a road network; geometry is the line drawn on the map; ETA is estimated arrival time.
GPS / accuracy / coordinateGPS is satellite-based location; a coordinate is latitude/longitude; accuracy estimates the likely location error.
Weather forecast / advisoryForecast is model-based expected conditions; official advisory/warning is an issued statement by the authority. They must not be conflated.
Push notificationServer-to-device alert delivered through platform push infrastructure; permissions/network/provider state affect receipt.
SMS gatewayService/device that sends or receives text messages through an API; API acceptance is not carrier delivery proof.
PTT (Push-to-Talk)Press-to-speak workflow; this project records/uploads internet voice clips, not radio frequency transmissions.
WebSocket / realtimeWebSocket is a long-lived two-way network connection; realtime usually means updates without waiting for a manual refresh. Requires server/provider configuration.
Provider acceptance / delivery receiptProvider acceptance means the provider accepted a request; a delivery receipt is stronger evidence that a device/carrier delivered it. Neither proves a human read/acted on it.

How / what / where / why — example answers

“How does a responder status update reach operations?” The responder uses the mobile app; it sends an authenticated API request; Laravel checks caller/device and validates data; a workflow saves the update; operations reads the resulting status from the API. A separate alert or partner exchange is another configured step, verified independently.

“How are external systems connected?” SafeTrack has authenticated household API sync/report clients; EvaTrack has a configured report API client and report exchange routes; TrackingAid has report API code and a separate resource-request database bridge/outbox. Live availability still requires environment configuration and partner acceptance evidence.

“How does offline work?” Selected rescuer snapshots, route data, downloaded tiles, GPS points and queued sync events can live on the device. Once online, the mobile app uploads supported events to the Laravel sync endpoint, which validates device/team/assignment and returns acknowledgements. Other features still need connectivity.

“Can we say every alert is delivered?” No. Describe the channel, backend job and provider response; prove actual device/carrier receipt with delivery evidence.
